# Self Upgrade (TPM playbook)

## Purpose
Learn from new Claude CLI releases and fold notably incremental, documented, revertible improvements into Ghola itself, then bump VERSION and commit and push. This is opt in and user triggered: you run it when the operator asks. It is not a background monitor. Ghola modules are session time instructions, so "monitoring" means checking the changelog during a run you were told to start, not watching for releases between sessions.

## Project-Ghola precondition (check FIRST)
Self Upgrade operates ONLY on the Project-Ghola repo itself — it folds new Claude CLI capabilities into Ghola's own modules, cores, and VERSION, so any other repo is out of scope. Before Detect/Analyze (alongside the War Mode precondition below), confirm the cwd/work-repo IS Project-Ghola: its `package.json` name is `ghola` (the package.json name is the robust signal — it survives clone renames; a `modules/` dir is a corroborating hint). The boot probe already emits this as `self_upgrade_repo=ok`/`wrong` in a self-upgrade session; you may also check directly. If the work repo is NOT Project-Ghola (`self_upgrade_repo=wrong`, or its `package.json` name is not `ghola`), REFUSE the entire run: tell the user Self Upgrade only runs in Project-Ghola, name the current repo, and instruct them to `cd` to Project-Ghola and relaunch. Do NOT Detect, Analyze, Propose, apply, commit, or push anything — stop immediately. This guard is checked FIRST, before any workflow step.

## Ghola mode precondition (check FIRST)
Before any of the steps below, check whether War Mode (`modules/mode.war`) is enabled for this session (it is toggled from the Agents tab, so it can be composed alongside self upgrade). If War Mode is ON, its CRITICAL SAFETY floor forbids ALL git writes (`commit`, `push`, `add`), and that floor is inviolable and dominant over modules. Self upgrade orders git writes, so under War Mode it MUST NOT run its commit, record, or push steps and MUST NOT stage anything. Defer the entire run: report to the user that self upgrade cannot commit while War Mode is active, and ask them to run self upgrade in a non ghola session (or disable War Mode first). Ghola's floor wins; self upgrade never attempts to override it. You may still perform the read-only Detect and Analyze steps to preview candidates, but stop before applying and never commit.

## Workflow

**RUN-START RECONCILE (do this before Detect).** An interrupted prior run can die after one or more per change commits (step 6) but before the trailing record commit (step 7), leaving local commits that are AHEAD of the recorded ledger baseline: the code is committed but no ledger entry, no last processed version update, and no VERSION bump was written for it. Before proposing anything, check for this drift. Compare local history against the recorded ledger state: look for local commits whose changes have no matching ledger entry (their hashes are absent from `parameters.changeLogPath`), and check whether `VERSION` disagrees with the last recorded run in the ledger. If the working tree or local history is ahead of the ledger, RECONCILE FIRST, before analyzing or proposing new changes: either complete the missing record commit for those orphaned changes (append their ledger entries with the captured commit hashes, advance the last processed version, and bump `VERSION` exactly as step 7 would have) or, if you cannot confidently reconstruct what the interrupted run did, surface the inconsistency to the user and stop for their guidance. Do NOT re-read the old baseline and re-propose or re-apply on top of unreconciled drift: that path re-analyzes changes that are already committed and yields empty commits and duplicate ledger entries. An interrupted run must be detected and healed here, not silently re-applied. One exception: if War Mode is active (see the precondition above), this reconcile CANNOT heal the drift here, because completing the missing record commit is a git write and Ghola's floor forbids all git writes; in that case report the pending inconsistency to the user and defer, so the drift is surfaced rather than silently carried, and let the reconcile happen in a non ghola session.

1. **Detect (establish the baseline).** Read `parameters.changeLogPath` to find the last processed Claude version recorded in the ledger, then WebFetch `parameters.releaseNotesSource` to collect what is new SINCE that version. If the URL fails to load or the content looks stale, fall back to a WebSearch for "Claude Code changelog" or "Claude Code release notes" and reconcile what you find against the last processed version. If there is NO readable last processed version (the ledger file is missing, this is the first ever run, or the recorded version string is unparseable), treat this as a FIRST RUN: do NOT bulk apply the entire changelog. Establish the baseline from the current Claude version and apply nothing without explicit user scope, OR ask the user which baseline version to start from. Only once a baseline exists does a run process the delta above it.
2. **Analyze (SWE fan out).** Dispatch SWEs to divide and conquer. Map each new Claude capability against Ghola's modules and cores, looking for where it enables a faster boot, cleaner instructions, or a genuinely new capability. This is judgment heavy, so use the parallel SWE pattern: split the release surface across SWEs and have each report candidate matches.
3. **Propose.** Assemble a short, ranked list of candidate changes. Each candidate states a rationale and an explicit gain claim (faster or more cutting edge). You may propose more candidates than `parameters.maxChangesPerRun`, but that setting is a hard cap on how many actually get APPLIED in this run: rank the proposals and only the top N up to the cap proceed. The cap enforces incrementality. Skip low gain or speculative changes.
4. **Approval gate.** Present the ranked proposals to the user and get approval on which to apply. Skip this gate only when `parameters.autoApply` is true. Treat this like a preview: nothing is applied until the operator says which candidates go forward.
5. **Plan disjoint commits (overlap check).** Before applying anything, compute the set of source files each approved change would touch. Every per change commit in a run must have a DISJOINT file set from the others, because `git add <file>` stages the whole file and a shared file would make one change's commit swallow another (so `git revert` of the later change would also revert the earlier one). If two approved changes would touch the SAME file, resolve the overlap before applying: either MERGE them into a single change committed once (one revert unit, logged as ONE ledger entry that covers both), or DEFER the second to a later run. Do not apply two changes with overlapping file sets as separate commits.
6. **Apply, verify, and commit each change.** For each approved change, in ranked order, run this sequence in full before moving to the next: (a) APPLY the edits to that change's source files, with a one sentence explanation; (b) VERIFY: if `parameters.requireVerification` is true, build plus typecheck plus QA must pass, and a red build blocks this change (do not commit it, skip to the next); (c) COMMIT that change by staging ONLY the files it touched with `git add <those files>` (never `git add -A` or a blind stage of the whole tree) and making ONE commit for it, so the commit is the revert unit; (d) CAPTURE the resulting commit hash. The commit MUST come before the ledger entry, because the hash only exists after the commit. Do NOT stage `VERSION` or the ledger file in these per change commits: they are not files a change touched, and they are handled by the record commit in step 7. This keeps each change's commit a clean revert unit whose `git revert` touches only that change's code.
7. **Record the run (ledger + VERSION), one trailing commit.** After ALL approved changes are committed (step 6) and their hashes captured, do the run's bookkeeping in ONE final "record" commit: (a) append one ledger entry per applied change to `parameters.changeLogPath` (date, the Claude version that inspired it, files touched, rationale, and that change's commit hash as the revert handle); (b) update the recorded last processed Claude version in the ledger to the version this run processed; (c) bump `VERSION` per `parameters.versionBump`. Then stage ONLY the ledger file and `VERSION` and make ONE commit (the record commit). Batching the ledger and VERSION here, separate from the change commits, is required for two reasons: a commit cannot contain its own hash, and keeping VERSION and the ledger out of the change commits means `git revert <change-hash>` reverts only that change's code and never the version bump or ledger. This record commit is where VERSION, all ledger entries, and the last processed version get committed, so nothing is left uncommitted at push time.
8. **Push.** Push per `parameters.commitAndPush`: `on-approval` asks the user first, `auto` pushes after verification passes, `off` never pushes and leaves the change commits and the record commit local. A push sends all of this run's commits (every change commit plus the record commit) to the current branch (main) with `git push`. All three git commands (`git add`, `git commit`, `git push`) are enabled for this profile via `tool.git`; follow tool.git's allowlist and refusal rules for the mechanics. Before pushing, self upgrade DEFERS to tool.git's `parameters.protectedBranches` guardrail: if the current branch is a key in that map, self upgrade REFUSES the push, reports to the user, and stops at the push step. It does NOT push and does NOT authorize around that guardrail. The Self Upgrade path relies on tool.git shipping `protectedBranches` empty (`{}`) by default, so the common case (an unprotected branch) pushes normally; but if the user has protected the current branch, self upgrade surfaces that and leaves the commits local. When the branch is not protected, the push is still subject to `parameters.requireVerification` (a green build, typecheck, and QA first) and the `parameters.commitAndPush` approval gate. `tool.github` (gh) is also available in this profile for GitHub interactions: by default only read-only gh is enabled, so after a push you may check CI run status with `gh run list` / `gh run view` when those commands are enabled. Broader gh operations (releases, PR merge, and the like) require enabling those commands in `tool.github` and are NOT part of the default commit path.

## Post-commit hook coordination (Ghola repo only)
When self upgrade runs in the Ghola repo, a post-commit git hook (`.githooks/post-commit`, wired in via `core.hooksPath`) fires on EVERY commit and runs `npm run package` (build) plus the VSIX install plus creating the `vX.Y.Z` tag from the VERSION file. Left uncoordinated, that means every per change commit in step 6 triggers a full package/install (N redundant builds — self upgrade already builds per change via `requireVerification`) and only the trailing record commit tags the right version. Coordinate so the hook fires EXACTLY ONCE per run:

- In step 6c, prefix each per change commit with `GHOLA_SKIP_HOOK=1` (i.e. `GHOLA_SKIP_HOOK=1 git commit ...`) so those commits do NOT each trigger a build/install/tag. The per change commits stay pure revert units and skip the hook.
- Let ONLY the trailing record commit in step 7 (the one that bumps VERSION) run WITHOUT the skip. That single un-skipped commit fires the hook once, which builds and installs the new VSIX and creates the `v<new-VERSION>` tag from the just-bumped VERSION.
- The HOOK owns build, install, and tag. Self upgrade does NOT tag itself and does not run its own package/install for the release — it just makes the commits and lets the record commit's hook do the packaging and tagging.
- This coordination applies ONLY in the Ghola repo, where the hook is configured. A client repo has no such hook, so `GHOLA_SKIP_HOOK=1` is harmless and irrelevant there — the prefix does nothing and the commits behave normally.

A companion `.githooks/pre-commit` hook makes `VERSION` the single source of truth: on every commit it auto-syncs `package.json`'s top-level version to `VERSION` and stages it (a no-op when already in sync). So on a commit where the hook runs, step 7's `VERSION` bump alone is sufficient — do NOT hand-edit `package.json` (it stays a protected file and is updated only by the hook by default; see "Version consistency verification" below for the single sanctioned hand-sync exception, used only when the hook path is unreliable and the operator explicitly approves), and this keeps the VSIX version (vsce reads `package.json`) and the `vX.Y.Z` tag (post-commit reads `VERSION`) consistent with the bumped `VERSION`.

`.githooks/pre-commit` also runs the parity gates registered in its `PARITY_CHECKS` array, which is the authoritative list of which gates exist and which files trigger each one: `scripts/ghola-path-parity.mjs` checks the host-path translation copies, and `scripts/ghola-statusline-parity.mjs` checks the statusline state-key copies. The step 6c `GHOLA_SKIP_HOOK=1` prefix suppresses every registered gate along with everything else pre-commit does, so every per change commit in a self upgrade run gets no parity check regardless of what it touches. The record commit does not pick up the slack either — a gate only fires when the staged set includes one of its own trigger paths (or the checker itself), and step 7 stages only the ledger and `VERSION`. So a self upgrade run that edits any of the triplicate files either gate covers can land fully committed with parity never verified — exactly the silent drift the gates exist to catch, and it has already happened once. Whenever a run touches a file either gate covers, check `PARITY_CHECKS` in `.githooks/pre-commit` for the current trigger list, then run the matching checker (`node scripts/ghola-path-parity.mjs` and/or `node scripts/ghola-statusline-parity.mjs`) by hand and confirm it exits 0 before considering the run complete.

This changes nothing about the disjoint-commit logic, the ledger/record semantics, verification gating, or the push step's `protectedBranches` deference; it only keeps the hook from firing redundantly on the per change commits.

## Version consistency verification (Ghola repo only)
`VERSION` is the single source of truth, but a release is only CONSISTENT when three other fields ALL equal `VERSION`: `package.json`'s top-level `version`, and `package-lock.json`'s BOTH its root `version` AND its `packages[""].version`. Those are the only version reference points in the repo; the release is not consistent until all three match `VERSION`.

The pre-commit hook performs that sync, but ONLY on a git commit where `node` is on PATH AND `GHOLA_SKIP_HOOK` is unset. A GUI/editor commit, a node-less shell, or a skipped hook (the step 6c skip) does NOT sync them — producing a `vX.Y.Z` tag whose `package.json` and lock still read the PREVIOUS version. Treat the sync as hook-dependent, never automatic.

Therefore, whenever `VERSION` is bumped:
- Do NOT report the bump "done" or a batch "ready to submit" without stating the ACTUAL current value of all three fields. A bumped `VERSION` sitting over a stale `package.json`/lock in the uncommitted working tree is an EXPECTED transient state — call it out honestly and name the values rather than implying consistency.
- If the operator will (or might) commit via a path that could skip the hook, ensure consistency explicitly BEFORE the release is tagged: either have them commit from a shell with `node` on PATH so the hook runs, OR — with the operator's explicit approval to edit the protected `package.json` — hand-sync `package.json` and `package-lock.json` (both its root `version` and `packages[""].version`) to `VERSION` so all three agree. This is the sanctioned exception to "do NOT hand-edit `package.json`": the hook owns the sync by default, and a hand-sync is permitted ONLY when the hook path is unreliable AND the operator explicitly approves the protected-file edit.
- Never present a batch as submittable while `VERSION` and `package.json` disagree without flagging the discrepancy and stating how it will be resolved (a hook-active commit, or an approved hand-sync).

## Ledger and revert model
The ledger at `parameters.changeLogPath` is append only. One commit per applied change (built in step 6), each logged in the ledger with its hash, so reverting a specific upgrade is `git revert <hash>` for that entry. The ledger is the map from change to commit. A change commit stages ONLY that change's source files and NEVER `VERSION` or the ledger, so a revert of it touches only that change's code. The ledger entries, the last processed version update, and the `VERSION` bump are committed together in the run's single trailing record commit (step 7), never inside a change commit; this is what keeps each change a clean, independently revertible unit and is why a commit is never asked to contain its own hash. Because two changes in one run can name the same file, step 5's overlap check guarantees the per change commits have disjoint file sets, so no change commit ever swallows another and each `git revert` is precise.

Entry template:

```
## <YYYY-MM-DD> upgrade: <short title>
- Inspired by: Claude Code <version>
- Files touched: <path>, <path>
- Rationale: <why this was worth applying and the gain it delivers>
- Commit: <hash>
```

Keep a single line near the top of the ledger recording the last processed Claude version, and update it at the end of each run.

## Safety floor (non negotiable)
- War Mode dominates. If `modules/mode.war` is enabled for the session, its CRITICAL SAFETY floor forbids ALL git writes (`commit`, `push`, `add`) and is inviolable and dominant over modules. Self upgrade MUST NOT run its commit, record, or push steps, and MUST NOT stage, under War Mode; it defers the whole run and tells the user to run self upgrade in a non ghola session (or disable War Mode first). Self upgrade never attempts to override Ghola's floor. Ghola's floor wins.
- Human in the loop is the default. Nothing applies, commits, or pushes without approval unless the auto settings (`autoApply`, `commitAndPush: auto`) are deliberately turned on.
- The immutable cores and hard rules floor is off limits. Self upgrade changes are strictly subordinate to it. Precedence: immutable cores plus hard rules > modules > self upgrade changes.
- Protected files require explicit user approval before any edit. The set is: `package.json`, `tsconfig.json`, `esbuild.config.js`, `tasks.json`, `launch.json`, the immutable cores (`prompts/cores/`), any file's safety floor, hard rules, or allowlist content, and specifically `modules/mode.war/ghola.md`'s CRITICAL SAFETY floor, `modules/tool.git/git.md`, `modules/tool.github/github.md`, and `self-upgrade.md` itself.
- Self upgrade must NEVER edit a safety floor, a hard rules block, an allowlist, or its own conditioning without EXPLICIT user approval, and such edits are NEVER applied autonomously even when `autoApply` is on. A self upgrade improvement may not touch a guardrail. If it believes a floor should change, it must surface that to the user as a proposal and never apply it.
- Commits are verification gated when `requireVerification` is true: a red build blocks the commit.
- `commitAndPush: auto` ALWAYS verifies. A push is NEVER made without a green build, typecheck, and QA, regardless of the `requireVerification` setting. This is a non negotiable floor: the compound of `commitAndPush: auto` plus `autoApply: true` plus `requireVerification: false` must NOT silently push unverified work to the current branch. Under `auto`, verification is mandatory even if `requireVerification` is off.
- Before any push, defer to tool.git's `parameters.protectedBranches`: if the current branch is a key in that map, refuse the push, report to the user, and leave the commits local. Self upgrade never pushes to a protected branch and never authorizes around that guardrail.
- The git grant this profile carries is deliberately narrow: add ONLY the files this run changed, commit, and push to the current branch (main). Nothing more is enabled. Every destructive git operation (force push, reset --hard, branch delete, history rewrite, and the like) stays forbidden, and the `tool.git` allowlist enforces this because only `git add`, `git commit`, and `git push` are enabled for the profile.
- Never expand a destructive git or otherwise unsafe capability under the banner of an upgrade. A self upgrade must never weaken a guardrail.

## Relationship to the no destructive git rule
The general posture, and this repo's own CLAUDE.md, forbids destructive git. Running the Self Upgrade profile is a DELIBERATE, user invoked EXCEPTION scoped narrowly to self upgrade's own verified and approved commits on the target repo. The user enabling the Self Upgrade profile and setting `commitAndPush` IS the authorization that permits these specific scoped commits. It does not grant any broader git write latitude, and everything else stays subordinate to the hard rules floor. This is the deliberate, bounded exception; it is not a general relaxation of the no destructive git rule.

## Settings reference
| Setting | Gates |
| --- | --- |
| `releaseNotesSource` | Where update info is fetched; WebSearch is the fallback if it fails or is stale. |
| `changeLogPath` | The upgrade ledger path; source of the last processed version and target for entries. |
| `maxChangesPerRun` | Hard cap on APPLIED changes per run; proposals may exceed it but only the top N up to the cap are applied. Enforces incrementality. |
| `autoApply` | Whether approved candidates apply without a per change approval gate. |
| `requireVerification` | Whether build, typecheck, and QA must pass before recording or committing. |
| `commitAndPush` | Push behavior: on-approval, auto, or off. |
| `versionBump` | How VERSION is bumped: patch, minor, or manual. |

## When it does NOT run and edge cases
- **First run / missing or unparseable ledger.** If the ledger file is missing (first ever run) or the recorded last processed version cannot be parsed, self upgrade does NOT bulk apply the entire changelog. It treats this as a first run: establish the baseline from the current Claude version and apply nothing without explicit user scope, or ask the user for the baseline version. Only then does a subsequent run process the delta above that baseline.
- **No stale re-apply after an interruption.** The last processed version update is committed in the SAME trailing record commit as the ledger entries and the VERSION bump (step 7). This closes the re-apply window: if a run is interrupted, an un committed baseline is never left behind for the next run to re-read as stale and re-apply the same changes. A change is only considered processed once the record commit that advances the baseline lands.
- **Already current.** If there is no new Claude release since the last processed version, report "already current" and do nothing.
- **Push command disabled.** If `git push` is not enabled in `tool.git` for this session you cannot push. Report and stop before the push step, or leave the commits local per `commitAndPush: off` semantics if the operator still wants the changes applied and documented locally.
- **Sources unreachable.** If `parameters.releaseNotesSource` is unreachable and the WebSearch fallback also fails, report and stop; do not guess what changed.
